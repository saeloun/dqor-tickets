# Private community workspace

This bounded slice comes from the reviewed tenant-owned community work in PR240 and its PR245 pagination follow-up, preserved in `dqor-organizer-foundation-20261012`. It starts from main `6eee2b9cfc89ea03ec2a3128cf0a525cc2fcda69`. Public group HTML, catalog APIs, publication actions and external discovery are excluded.

All three existing gates must be enabled in an authorized environment: `ORGANIZER_PLATFORM_ENABLED`, `FREE_EVENT_PILOT_ENABLED` and `MEETUP_GROUPS_ENABLED`. This change does not activate any gate. Existing verified organization owners and admins can create/edit private groups and start a linked draft event directly inside a group. Existing editors and viewers can read groups only. A fresh locked membership and tenant-scoped group protect each write. Saving an event does not publish it, create tickets, invite people or open registration.

The additive schema change is staged to avoid holding an exclusive event-table lock throughout an index build or a foreign-key scan:

1. `20261011030000` creates the group table and its indexes/check, then adds the nullable event column in one short transaction. Its local lock timeout is five seconds and statement timeout is twenty seconds. A brief exclusive lock on `events` is still required to add the column; a held reader can make this stage abort and roll back atomically.
2. `20261011030100` builds the existing organization/group/start-time event index concurrently, outside a DDL transaction, with a five-second lock timeout and ten-minute statement timeout. Both previous connection-session timeout values are restored in `ensure`. A failed build can leave an invalid index: retry checks its exact owned name, ordered columns and definition, drops only a matching invalid index concurrently and rebuilds it. A matching valid index permits a safe retry; a conflicting definition aborts for inspection and is preserved.
3. `20261011030200` adds the composite matching-organization foreign key as `NOT VALID`, in a short transaction with five-second lock and twenty-second statement limits. This still needs a brief write-blocking table lock, but does not scan existing events. New inserts and updates are immediately constrained after this stage commits.
4. `20261011030300` validates that foreign key separately, with a five-second lock timeout and five-minute statement timeout. PostgreSQL uses the lower `SHARE UPDATE EXCLUSIVE` event-table lock for validation; ordinary reads and writes can continue.

Existing event rows remain unlinked and their facts are unchanged. A timeout aborts the current stage; earlier successful stages can remain committed. Keep all group capabilities disabled throughout partial-stage recovery. Inspect the failed stage and its owned invalid index, clear the actual competing workload through normal operational coordination, then retry the pending migration. Do not mark a failed stage complete or activate the application before the index is valid and the foreign key is validated. These migration versions are for the unmerged candidate; an environment that already applied the earlier draft must be reconciled explicitly rather than assuming the first-stage source is rerun.

Deployment still requires actual migration rehearsal, backup and rollback readiness. Application rollback retains the additive schema, indexes and tenant constraint. All four migration down methods reject rollback: dropping group data, removing event links or removing tenant enforcement requires separate explicit approval and a reviewed data plan.

`script/verify_community_group_migrations.rb` is an opt-in local rehearsal, outside the default RSpec suite. It accepts only a `COMMUNITY_MIGRATION_DATABASE_URL` for a prepared 72-event synthetic scratch database named `dqor_community_migration_*` on local port 53448, with no group table or event link present. `staged` mode exercises the bounded held-reader abort, actual concurrent-build cancellation/invalid-index retry, immediate cross-tenant insert/update rejection and final validation. `baseline PATH` requires the exact retained original migration SHA and demonstrates its lock contract. Controlled SQL-notification pauses compare independent reader/writer behavior; they are not timing benchmarks. The harness explicitly supplies the same DDL transaction boundary as Rails Migrator and does not run destructive downs, reset databases or mark migration versions complete.

Real group creation, organizer access grants, public group publication, registration activation, billing, credentials and production feature settings remain separate approval/release gates. The conference, public owned-event API and native application sources are preserved.
