## State and privacy

A memory-only transaction creates independent random 256-bit state and PKCE verifier, derives S256, and expires after ten minutes of app-relative Swift ContinuousClock time, which advances during device sleep. The callback must use the canonical HTTPS host/path without port, user information, fragment or encoded host/path alternatives. It accepts exactly one code and state, rejects duplicates, bounds URL length and validates the `nac1_` code shape. Both browser completion and an external `onOpenURL` return consume the same active transaction once. External return resolves the browser continuation before canceling the owned browser session. Cancel, Back, timeout, cold restart and old callbacks fail closed. Backgrounding preserves a bounded pending browser transaction because email verification may occur outside the app.

The bearer lease is opaque `na1_` plus 43 URL-safe characters. Token/code descriptions are redacted. Account, pass DTOs and tokens remain in memory, separate from the public programme and staff Keychain. The accepted absolute expiry is capped at thirty minutes and also gets a ContinuousClock deadline and generation-bound expiry task. Idle expiry clears private information without requiring a new request. Logout clears local state immediately, then attempts one bounded revocation. A failed revocation retains only a bounded in-memory removal handle for an explicit manual retry; it never queues automatic retries. A separate ContinuousClock expiry task drops an idle expired removal handle and cancels its owned request without another server call. A known late exchange result is discarded and receives this bounded removal treatment. Unconfirmed removal relies on server absolute expiry and persistent backend revocation rules.

Every private await checks generation and expiry before starting another read or installing results. Refresh, reentry and foreground revalidate the session before reading account and passes. During private-view backgrounding an opaque overlay hides account content. Connectivity failures retain memory-only observations with visible “not revalidated” copy; they cannot supply a QR, fresh eligibility or attendance. Any read 401, invalid private response, changed identity/client/capabilities or expired session clears credentials and DTOs. Server `checked_at` is preserved separately for the account and each pass page. Recorded entry timestamps describe previous observations, not re-admission authorization.

Pagination accepts positive canonical Int64 identifiers in ascending order, checks cursors against the last row, rejects duplicates/cycles and caps displayed records at 200. The limit keeps valid account information and provides the official website for further records. Nullable name, admission dates and check-in time remain nullable. Pass records show read-only status; there is no QR or wallet credential implementation.

## HTTP adapter

The adapter follows PR #192's exact token JSON without `schema_version`, refresh token, bearer header or query. Read/delete requests use the exact bearer header and fixed `/api/native/attendee/v1/` routes. The transport independently validates the canonical origin, path, method, query, body and header allowlist before URLSession. A dedicated ephemeral session has no cookie store, credentials, URL cache, additional headers or redirects. Normal system TLS remains required. Requests/resources are limited to 20/30 seconds; streamed JSON is bounded to 256 KiB. Token and session responses reject unexpected fields. Typed status/code pairs distinguish exchange `401 invalid_grant` from read `401 unauthenticated`; a mismatched 401 is invalid data and clears the private session. Rate limit requires `Retry-After: 180` and waits for an explicit retry.

Debug `--attendee-auth-fixture` exposes clearly labeled fictional account rehearsal only. `--public-fixture` keeps the associated programme synthetic. `--attendee-older-policy` injects unsupported callback capability for tests. The fixture and its UI entry are compiled out of Release. A URLProtocol fixture intercepts canonical HTTPS requests in memory; it is not a deployed bridge or a loopback HTTP server. Production default remains unavailable regardless of process arguments.

## Platform and activation gates

The existing bundle remains `org.dqor.staff` and the deployment target remains iOS 17.0. The owner-approved canonical client/callback mapping is `dqor-ios` with `https://deccanqueenonrails.com/native/attendee/ios/callback`. No custom callback scheme or minimum-version increase was introduced.

The installed SDK requires iOS 17.4+ for `ASWebAuthenticationSession.Callback.https`. Its HTTPS callback requires a `webcredentials` associated-domain entitlement and matching AASA `webcredentials.apps`. Email verification/consent may complete in a different Safari/Chrome browser, so independent universal-link delivery additionally requires the `applinks` entitlement and corresponding AASA path association. Both returns route to one strict active transaction; cold returns reject. These associations, signing assets and registry entries have not been provisioned or tested. iOS 17.0–17.3 uses the official system-browser account fallback. The availability test injects that policy on an actual iOS 26.5 simulator; it is not an actual iOS 17.3 test.

Before any activation, independently approve backend deployment/flag, exact client registration, both verified domain associations, team/App ID/provisioning, secure browser/email consent scope, real-device return routing and revocation tests. This implementation cannot prove physical ASWebAuthenticationSession routing, external email-browser universal links, TLS interaction with the undeployed private service, production attendee eligibility, secure QR display, staff scanning or distribution. No real account, email, payment, ticket, attendance, production flag, entitlement or credential was changed. Root owns mandatory five reviews, commits, PR and Library publication; the auth diff remains uncommitted until those reviews complete.
